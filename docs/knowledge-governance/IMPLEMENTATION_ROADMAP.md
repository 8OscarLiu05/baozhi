# 实施路线图

以下为方案确认后的工程估算，按一名工程人员的有效人日，专业审核和官方资料取得另计。每个阶段可单独验收。涉及的新文件名是提案，实际开发在独立 Git 分支，先使用临时库或一致性副本。

| 顺序 | 工作及预计文件 | 估算 | 依赖 / 主要风险 | 验收 |
|---|---|---:|---|---|
| P0 基线与隔离 | app.py 的启动配置、tests/、新增迁移和回归夹具 | 2–3 人日 | 确认方案及旧样例政策。默认启动会写库 | 可明确指向副本；两版旧入口有基线；数据库与资产备份可恢复 |
| P1 知识数据核心 | 新 knowledge_store.py、迁移模块、app.py 接口、权限测试 | 4–6 人日 | P0。旧产品 ID/版本映射误认 | 实体约束通过；旧 ID 兼容；候选与旧 published 均不进入正式视图；迁移可重入 |
| P2 最小输入闭环 | 新 knowledge_ingest.py、knowledge_validation.py、app.py、审核/API 测试 | 5–8 人日 | P1、至少一份合规官方原件。解析与引用质量 | 原件可验哈希；一个版本从登记到审阅、发布、撤回；失败重试幂等。先把高风险字段做实 |
| P3 双版本前端与试点扩展 | static/classic/app.js、static/app.js、相关 CSS 和浏览器测试 | 4–7 人日 | P2。表格/OCR 与专业审核排期 | 资料、任务、证据、审核、发布界面可用；累计 2–3 份正式合同或明确阻塞；同类错误可统计 |
| P4 统一读取与受控输出 | app.py、clause_query.py、consultation.py、portal_hub.py、现有前端证据卡 | 5–8 人日 | P1–P3 已有审定快照。频道差异、旧证据退化 | 展业、客户、电话、专业咨询同版本同事实；影子比对与开关回滚；注入、错版、缺证据、模型故障通过 |
| P5 独立复核与上线准备 | tests/、验证工具、迁移/恢复手册、操作说明 | 3–5 人日 | P4，专业审核与真实身份接入计划 | 达到风险验收门槛；历史记录可回看；上线审批、回退演练和权限演练完成 |

工程估算 23–37 人日，取决于文件质量与需对接的身份系统。OCR、复杂表格和专业审核从真实样本测量再修订。先做 P0/P1，再用一份合同打通 P2，确认边界后才扩页面、产品和业务入口。生产身份、备份和资料合规未验收前，维持本机演示范围。第一阶段交付后停在方案评审。
